# portable-devshell v1.0.0-alpha.3

This is the third **1.0 prerelease**, focused on Reverse tool routing, execution environment extensibility, persistent agent Memory, and recovery under weak networks or partial component failure. It is for controlled evaluation, **not** a stable release.

## Highlights

1. **Restored explicit cross-Instance MCP tool routing.** Worker-facing tools again expose an optional `instance` selector. After `environ_remote attach`, tools can target an attached Reverse Instance through the *same* MCP endpoint and the unified ToolCall ingress. Routing metadata is removed before Worker validation; invalid or masked targets are rejected before execution. The isolated Testspace smoke now exercises this same-endpoint flow instead of switching to a dedicated Reverse MCP endpoint.
2. **Execution environment and sandbox Extension points.** Instance execution can prepare environment contributions and a selected sandbox for Worker processes. Worker-local `direnv` support is provided through the execution environment extension mechanism.
3. **Agent Memory and collaboration.** `devshell memory init` and `devshell memory inherit` establish or reuse a named Memory directory and its associated agent-work/mailbox identity. Comment mailing and environment discovery preserve those bindings without creating a new Memory for every Context.
4. **Weak-network and partial-failure tolerance.** Control reconnects reauthenticate; transient channel setup retries avoid replaying committed calls. MCP uses JSON for short responses and keeps long-running tool calls alive through SSE. Audit, outbound delivery, historical Context cleanup, optional Host activation, and Extension sandbox failures are isolated so that unrelated operations can continue and completed ToolCall outcomes remain inspectable.
5. **Operational and MCP App fixes.** Improvements cover retained output/audit provenance, inline previews, model-output budgets, configuration recovery, disabled or degraded instance handling, and Windows package smoke failure propagation.

## Known limitations and precautions

- **Destructive Worker garbage collection: do not run `devshell-worker gc` on a host with valuable stopped Instances.** In this alpha, a valid but stopped Instance can be selected for retirement, including its local configuration, logs, and artifacts. `gc --dry-run` is suitable for inspection only; automatic garbage collection and safer eligibility rules are deferred.
- **Re-enrollment can retire local state.** Re-enrolling a Worker with an existing Instance name may stop and retire the previous local instance, including local data. Back up the existing instance before re-enrolling and avoid name collisions across Controls.
- **Worker Host supervision is not yet implemented.** A Worker installation may run separate daemons for separate Instances, but there is no unified host supervisor, Instance listing, process restart policy, or coordinated binary rollout. Those architectural changes are deferred to Beta.
- **MCP tools do not implicitly switch machines.** `environ_remote attach` grants the current Context access to a remote environment; specify the intended `instance` on Worker tool calls. Existing ChatGPT sessions may need their MCP tool catalog refreshed after upgrade.
- **Alpha upgrade rules still apply.** Back up configuration and persistent state, and use the supported configuration/database schema versions. Older Control/Worker binaries and arbitrary historical persistent schemas are not guaranteed compatible. The Agent Extension and its model-provider runtimes remain separately managed.

## Verification and release gate

- On Linux x64, focused MCP regression tests, TypeScript source/test checks, MCP build, and isolated Testspace smoke passed. The smoke covers real Rust Reverse Worker execution through the original MCP endpoint, explicit instance selection, and rejection after `mask`.
- An independent Reverse Mac was exercised using the same model-facing `bash_run` tool with `instance: "reverse-mac"`; it reported macOS/Darwin, while `instance: "aromatic-pc"` reported Linux.
- Formal multi-platform CI and the six-target application/Worker artifact builds, SHA-256 checksums, and installer smokes remain release-workflow gates; passing local tests alone does not establish all-platform compatibility.

See `docs/development/compatibility.md` and `docs/development/acceptance.md` for supported contracts and acceptance scope.
