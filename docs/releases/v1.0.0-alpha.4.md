# portable-devshell v1.0.0-alpha.4

This is the final planned **1.0 Alpha** release. It focuses on real-world
recovery, safer Instance lifecycle operations, and clearer Reverse Worker
status and controls. It remains a prerelease; no stable-API or exactly-once
execution guarantee is implied.

## Highlights

1. **Reverse Worker enrollment and recovery.** Connection state now
   distinguishes pending enrollment, offline Workers, and stopped daemons.
   Failed pairing no longer looks successful or silently discards the Instance.
   TUI supports pairing-code management and credential revocation. A working
   credential/channel remains available until replacement activation succeeds;
   failed activation restores the previous connection. Candidate verification
   stays on its own channel: ordinary RPC traffic remains on the old connection
   until the replacement handshake and peer-cutover acknowledgment complete.
2. **Safer deletion and name reuse.** Control commits Instance removal without
   holding its global configuration lock through Worker retirement or Context
   cleanup. Concurrent recovery joins in-flight cleanup rather than repeating
   destructive operations; same-name recreation cannot overtake the old
   generation's unfinished cleanup. Unreachable remote resources are reported
   as orphaned without reusing their old name for a destructive cleanup retry.
   Worker garbage collection is coordinated with active Instance lifecycles.
   Disable, Rebuild, and batched Instance configuration changes now reserve the
   same cleanup owner and release the global configuration lock before Worker
   or accepted ToolCall draining. A failed old-generation close retains debt
   rather than incorrectly reporting successful cleanup.
3. **UI and audit durability.** WebUI retains historical Audit entries through
   refreshes, displays current Instance state and partial retirement warnings,
   and exposes Reverse connection and recovery state. TUI and WebUI distinguish
   committed configuration changes from pending resource cleanup.
4. **Worker state and partial-failure tolerance.** Stopped and re-enrolled
   Instances retain their local data. Reverse bridge reconnection preserves
   buffered completed Worker responses. A failed or stalled optional Comment
   Memory provider no longer prevents `environ_info` from returning the
   essential Context identity; the model-facing result is intentionally
   concise.

## Known limitations and precautions

- **Completed calls interrupted by a network break:** WSS does not yet have
  end-to-end application-result acknowledgments and deduplication. A send
  acknowledged by the transport is not proof Control persisted the result.
  Do not blindly repeat a command with side effects after an ambiguous
  disconnect; inspect Audit and execution state first.
- **Remote orphan cleanup:** Cleanup-debt records have Controller-side
  identities, but not all remote provider resources carry an immutable
  generation identity. Old unreachable resources may require inspection and
  manual cleanup. Automatic cleanup must not guess a remote target from its
  reusable Instance name.
- **Alpha compatibility:** Upgrades depend on supported configuration and
  database schemas, not an arbitrary historic executable version. Back up
  persistent state before upgrading. Model CLI permissions remain subject
  to per-Instance Extension allowances.

## Verification and release gate

- Linux x64 development CI covers compatibility expiry, script tests, Lint,
  builds, TypeScript/Domain checks, Rust workspace tests, Worker tmux contracts,
  and package/extension tests.
- The isolated v0.7.7-to-alpha.4 upgrade matrix covers eight installation,
  recovery, rollback, schema and fault-injection scenarios.
- Real MCP client and Chromium WebUI smoke tests cover ToolCall output
  recovery, Audit retention, and Instance lifecycle operations.
- **Formal release still requires** successful `dev*` CI for the exact
  release commit, including platform/packaging targets, verified checksums,
  and installer validation. Local passing tests alone do not satisfy that
  cross-platform release requirement.

See `docs/development/compatibility.md` and
